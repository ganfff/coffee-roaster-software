# 后端、控制与硬件参考

在修改 FastAPI、WebSocket、Pydantic、SQLite、烘焙控制器、状态机、配置、TC4S 或 RS485 时读取。先在 `roaster/PITFALLS.md` 搜索对应模块与故障模式；以下内容不能替代当前代码或设备手册。

## 代码边界

- `roaster/main.py`：应用入口和静态资源服务。
- `roaster/src/web/web_api.py`：REST 与 WebSocket 边界。
- `roaster/src/core/`：模型、状态、ROR/曲线与控制行为。
- `roaster/src/services/data_manager.py`：曲线和记录持久化。
- `roaster/src/hardware/tc4s_async.py`：TC4S Modbus RTU 通信。
- `roaster/config.yaml`：串口、轮询、预热和控制参数。

先搜索创建点、调用方、序列化模型、模拟器镜像契约和前端消费者，不假定这份列表永远完整。

## API、状态与数据

- 协议变更同时核对 REST 路由、WS 命令/回包、状态 payload、模拟器和客户端消费方。能兼容旧字段时优先兼容；不能兼容时提供明确迁移。
- 保留 `{ok}` / `{error}` 入口短路，错误必须对用户可观察，不能伪装成普通状态帧。
- 后端的 `profile_id`、`profile_name` 和烘焙状态是活跃会话可信源；客户端本地选择不能反向覆盖真实状态。
- 检查无效输入、空数据、断线重连、重复命令、并发事件和取消路径。状态转换应显式证明允许与禁止的边。
- `asyncio.Lock` 不可重入；避免在状态锁内等待串口/数据库等慢 I/O。串口写入序列化、任务取消、回调异常与资源关闭要有清晰归属。
- 模型或 SQLite 结构变化要读取旧记录、旧配置和缺字段数据；默认值、单位、浮点/整数转换及迁移必须有测试证据。

## 硬件安全

- 任何寄存器变更都核对设备资料中的地址、功能码、读写权限、数据类型、缩放、单位、范围和字节序，并在代码附近保留可维护依据。
- 超时、重试、退避、CRC、重连和 ERROR 行为应与当前协议时序及配置一致。不要无依据统一成某个重试次数或退避算法。
- 通信失败后的安全目标是停止新增加热请求、进入可观察故障状态并尽力发送安全输出；如果设备已离线，软件命令可能无法真正关断，所以必须保留独立硬件过温与断电保护的事实边界。
- 急停、结束、ERROR、取消和冷却之间要审查竞态。任何异常或传感器无效都不能形成加热器持续开启的新路径。
- 串口轮询不得被普通 API 请求、数据库写入或日志阻塞；同时避免过密重试压垮总线。
- `roaster/tools/tc4s_test.py` 属于真实设备工具。只在用户明确授权、目标树莓派与端口已确认、人员可以观察设备且具备安全停机手段时运行。

## 分层验证

1. **主机安全检查**：语法/类型、纯函数测试、模型序列化、旧数据兼容、mock/fake I/O 和差异审查。
2. **协议模拟**：用仓库模拟器或受控 fake 验证 REST/WS、状态转换、错误传播和客户端契约；模拟器通过不代表 Modbus 正确。
3. **树莓派无负载验证**：确认依赖、设备枚举、权限、波特率/校验、超时与断线行为。
4. **受控真机验证**：从安全输出开始，监看 PV/SV、加热、急停、ERROR 与冷却；事先准备人工断电/过温保护。

只报告实际完成的层级。未运行后两层时，给出具体命令前先确认它不会超出用户授权，并明确仍存在的设备风险。
