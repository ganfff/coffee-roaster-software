# 文档与版本参考

在修改 `UPDATE_LOG.md`、README、`PITFALLS.md`、架构/迁移文档或 QA 证据时读取。文档服务于长期维护，不是每次代码编辑都要完成的仪式。

## 文档职责

- 根 `README.md`：统一工作区入口、模块边界、稳定命令和开发安全边界。
- `roaster/README.md`：核心服务、配置、运行、API/硬件和烘焙流程。
- `desktop/README.md`：Tauri 开发、模拟器、打包和平台限制。
- `docs/`：架构、分支迁移、设计基准和可复查 QA 证据。
- `roaster/UPDATE_LOG.md`：可发布、用户可见或重要兼容性变化。
- `roaster/PITFALLS.md`：容易复发、非显而易见且会改变后续决策的陷阱与安全契约。

## 何时更新

- 行为、配置、协议、依赖或发布内容变化：更新现有版本条目或按项目惯例新增版本。
- 模块边界、目录、安装、构建、部署或运维命令变化：更新对应 README/架构文档。
- 发现一个可复现、可推广的隐藏约束：写入 PITFALLS，包含原因、影响、规避/修复和相关文件。
- 视觉重构或用户明确要求证据：把尺寸、主题、场景、原生窗口与结果写入适合的 QA 文档。

以下情况通常不更新产品版本：只改本 Skill、本机工具配置、注释/错别字、没有行为影响的内部整理，或尚未形成可发布结果的实验。

## 写作规则

- 先读取目标文档最近条目与实际结构，延续当前格式和语言；不要套用过期模板，也不要为每条更新复制完整目录树。
- 不臆造版本号、日期、测试结果或设备验证。版本与日期从当前仓库和环境获得。
- 描述“改了什么、为何改变、影响/兼容性、证据、未验证项”，把实现细节控制在未来维护者真正需要的程度。
- 版本升级时同步所有真实版本来源。Tauri 发布版本当前至少涉及 `desktop/package.json`、`desktop/src-tauri/Cargo.toml` 和 `desktop/src-tauri/tauri.conf.json`，修改前搜索确认是否还有消费者。
- 文档链接、命令和路径要在当前工作树验证；分支外内容明确标注，例如 Flutter 源码位于 `feature/flutter-app`。
- 代码行为稳定后再定稿版本记录；随后检查文档 diff，避免把无关历史重新格式化。
