# 审查与验证参考

需要评估改动、设计验证策略或判断能否交付时读取。审查可以由当前执行者、独立人员、代理或专业工具完成；选择取决于风险、授权与可用性，不把某种审查载体写成硬要求。

## 先建立审查范围

- 重新读取用户请求与明确的非目标。
- 查看 `git status --short` 和聚焦 diff，区分本次改动与已有工作树改动。
- 列出受影响的生产者、消费者、持久化格式、配置、模拟器和文档。
- 对安全关键改动，单独列出故障模式、默认安全状态、回退方法与尚未验证的真实设备假设。

## 审查维度

1. **需求与范围**：用户要求是否完整实现；是否遗漏边界或引入无关重构。
2. **正确性**：正常、空值、非法值、断线、重复、并发、取消和恢复路径是否符合预期。
3. **跨层一致性**：REST/WS/模型/模拟器/客户端字段、单位、命名和错误语义是否一致。
4. **安全性**：加热、急停、ERROR、冷却、传感器异常与通信失败是否仍失效安全。
5. **兼容性**：旧配置、旧曲线、旧记录、本地存储、主题和分支边界是否保留或有迁移。
6. **体验与性能**：触控、键盘、焦点、主题、图表尺寸、高频更新、async 阻塞和资源释放。
7. **可维护性**：新增复杂度是否必要；本次改动造成的无用导入、失效选择器、旧事件或注释代码是否清理。

问题按影响报告，并给出文件与精确位置：

- **阻断**：可能伤害设备/人员、破坏数据、核心功能不可用或需求未实现。
- **重要**：高概率回归、契约不一致、错误处理缺失或验证不足。
- **建议**：不影响当前正确性的改进。

没有发现问题时明确写“未发现阻断或重要问题”，但不要把审查等同于运行时验证。

## 证据设计

验证优先覆盖最可能失败的行为，不为匹配措辞而写脆弱的正则测试。

- 每个需求至少有一种可观察证据：测试、命令输出、协议消息、持久化结果、原生窗口交互或真机行为。
- 每个修复都应有能在修复前失败、修复后通过的复现或等价回归检查；无法复现时说明证据限制。
- 使用当前环境实际可用的命令，并读取退出码和关键输出。缓存的旧结果不能作为本次证据。
- UI 视觉检查记录场景、窗口、尺寸和主题；硬件检查记录平台、设备、端口、负载和安全措施。
- `git diff --check`、语法检查或构建只证明对应层级，不证明业务或真机行为。

## 独立性按风险伸缩

- 低风险聚焦改动可以直接自审。
- 跨层或高回归面改动适合在实现后切换视角，重新按需求和完整 diff 审查。
- 安全关键改动优先获得未参与实现的独立复核；若当前没有授权或能力，执行严格二次自审并把“缺少独立复核”列为残余风险，不能假装已经获得。
- 并行工作仅用于边界独立、不会编辑同一文件或共享状态的部分；合并后必须审查交叉影响。

完成判定以证据为准：实现、直接相关清理、必要文档和当前可执行验证已完成；目标环境验证未完成的部分清楚标注，不以笼统“通过”掩盖。
