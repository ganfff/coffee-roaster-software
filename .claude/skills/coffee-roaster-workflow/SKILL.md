# 咖啡烘焙机工程工作指南

## 定位

本 Skill 提供项目语境、风险判断和硬件安全边界，不规定固定工作流。它自洽可独立使用，也不要求任何特定工具、代理架构、模型或外部 Skill。

根据任务自由组合直接执行、仓库脚本、专业工具、独立审查、并行协作或其他可用方法。用户显式点名的能力与更高优先级规则照常遵循；除此之外，只有在某项能力确实提高质量或效率、且符合当前授权时才调用。能力是否被调用不是交付质量指标，能力缺失也不应让普通任务停摆。

始终保留用户的范围和选择。先判断请求是回答、诊断、修改、审查还是验证；只被要求诊断或审查时，不擅自实现或扩展产品范围。

## 从任务出发

1. **确认影响面**：识别 Web 前端、Tauri、FastAPI/WebSocket、数据、控制状态机、硬件通信或文档中真正相关的部分。
2. **检查现状**：先看 `git status --short`，保护已有改动；搜索相关实现、调用方和契约，不凭旧目录印象改代码。
3. **按需取上下文**：跨模块改动先看根 `README.md` 和相关模块 README；行为、版本或发布相关改动查看 `roaster/UPDATE_LOG.md` 最近条目；触及敏感路径时在 `roaster/PITFALLS.md` 搜索相关主题。不要把通读全部文档变成仪式。
4. **先定义证据**：动手前决定什么检查能证明这次改动正确，以及哪些结论只能由树莓派或真实设备验证。
5. **完成最小闭环**：实现用户要求，处理紧邻的契约和清理，不顺带重构无关区域。

任务变复杂或变简单时可以随时调整方法，不需要先给工作方式贴标签，也不需要向用户展示内部编排过程。

## 风险决定深度

- **局部低风险**：文案、文档、隔离样式或明确的小型逻辑。读取相关文件并做聚焦检查即可。
- **集成风险**：REST/WebSocket、数据模型、持久化、状态机、跨页面交互、Tauri 配置。核对生产者与消费者，补充或运行契约测试、回归检查和可观察的运行时验证。
- **安全关键**：加热输出、温度边界、急停、冷却、TC4S 寄存器、RS485/串口/GPIO、故障恢复。先做离线分析和模拟验证；需要独立视角时可自由选择人工、代理或二次自审。没有目标树莓派/真机证据时，只能报告“主机/模拟器已验证，真机待验证”，不能宣布硬件行为完成。

文件数量、代码行数或是否使用其他 Skill 都不能替代风险判断。

## 项目边界

- `roaster/` 是 FastAPI、WebSocket、控制器、TC4S/RS485 和共享 Web 前端的核心。
- `desktop/` 是复用 `roaster/static/` 的 Tauri 2 原生桌面壳，并提供安全的本机协议模拟器。
- `docs/` 保存架构、迁移、设计基准和 QA 证据。
- Flutter 完整实现位于独立分支 `feature/flutter-app`；当前工作树没有该目录时，不要凭迁移文档假装已修改 Flutter 源码。
- 版本与命令以仓库当前文件为准，不把本 Skill 中的技术栈或版本说明当成永不变化的事实。

## 不可弱化的工程约束

### 硬件与人员安全

- 本仓库的 Windows 工作流只允许源码、静态检查、安全模拟器和桌面构建验证。不要启动可能打开真实串口或驱动加热器的完整后端，也不要在 Windows 运行 `roaster/tools/tc4s_test.py`。
- 真实 TC4S/RS485/GPIO 操作仅能在明确指定的树莓派和端口上、得到用户授权并确认设备处于安全状态后执行。
- 加热控制必须失效安全：无效传感器、通信丢失、异常状态或取消操作不得新增持续加热路径。软件关断命令不能替代独立硬件过温保护。
- 急停、ERROR、冷却和安全关断路径的可达性、优先级与可见性高于视觉或结构整洁。高风险改动应明确回退策略。
- 寄存器地址、功能码、缩放、单位、合法范围和字节序必须来自当前代码、设备文档或可追溯证据，不能靠记忆猜测。

### 跨层契约

- 修改 REST、WebSocket、Pydantic 模型或状态字段时，同时搜索所有 Web、Tauri、模拟器和可能的 Flutter 消费者；保持兼容，或明确迁移方案。
- 保留 WebSocket `{ok}` / `{error}` 回包入口短路、后端状态可信源及现有事件语义，除非用户明确要求改变协议。
- async 路径不得引入阻塞 I/O、锁重入、锁内长时间 await 或失控后台任务；资源关闭、取消和重连行为应可验证。
- 曲线、配置和烘焙记录变更要考虑旧数据读取、默认值、单位与迁移，不能只验证新建数据。
- 删除死代码只覆盖本次改动及其直接失效部分；不要借“清理”扩大到无关重构。

### 前端与原生体验

- `roaster/static/` 同时服务浏览器、树莓派 kiosk 和 Tauri WebView；修改共享资源时检查各入口。
- 保持当前 Calm Canvas 设计系统、深浅/跟随系统主题、离线资源、减少动效和触控可用性。图表、canvas 和动态模板不能绕过主题契约。
- 急停必须在普通模态与全屏视图中持续可见可用；编辑器必须保留 Pointer Events、指针捕获和 `touch-action: none` 等触控契约。
- 用户要求“打开 Tauri 看效果”时，交付证据必须来自安全模拟器驱动的原生 Tauri 窗口，普通浏览器截图不能替代。

## 验证与完成

选择能覆盖真实失败模式的最小充分验证组合：

- 静态与结构：语法、类型、格式、链接、资源和 `git diff --check`。
- 行为与契约：聚焦测试、API/WS 消息、持久化兼容、状态转换和错误路径。
- UI：`desktop` 中的 `npm run check:frontend`；需要交互或视觉证据时使用 `npm run dev:sim -- --freeze`，按相关场景在原生窗口验收。
- 硬件：主机/模拟器验证与树莓派/真机验证分开记录。不要把“代码可编译”写成“设备已验证”。

验证失败时先缩小问题、确认根因和假设，再做最小修复。没有新鲜证据时不要声称通过；无法在当前环境执行的检查要说明原因、影响和准确的后续步骤。

文档按影响更新，而不是每次机械更新：

- 用户可见行为、配置、协议或可发布版本变化，按现有格式更新 `roaster/UPDATE_LOG.md`。
- 架构、目录、安装或运维入口变化才更新相关 README。
- 新出现且可复用、非显而易见的陷阱才写入 `roaster/PITFALLS.md`。
- 仅调整本 Skill 或本机工作流说明，通常不提升产品版本。

交付时简洁说明结果、关键文件、验证证据、未验证项与真实风险。不强制固定模板。
